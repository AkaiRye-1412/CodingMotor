## 1. 项目主要目的

### 1.1 一句话定位

把资深电机选型工程师在 Excel 与厂商样册之间来回换算的过程，固化为一条**可复算、可对照、可交付**的本地流水线：

> 工况输入 → 运动规划 → 理论力/力矩 → 候选筛选 → 选定型号 → 实际应用值（热/电压/余量）→ 曲线与报告

### 1.2 解决的具体问题

| 手工现状的痛点 | 本产品的对应能力（需求出处） |
|---|---|
| 梯形/三角形、S 曲线的峰值速度与峰值加速度靠查表或经验，易算错 | 闭式公式 + 自定义反解 + 冲突显式报错（4.2 / FR-MOT-02） |
| 持续力要不要按 RMS 算、停机段算不算，各家口径不一 | 循环 RMS（含停顿段），并已与参考选型软件逐位对齐（5.1） |
| 热与母线电压常被忽略，只比"连续力/峰值力" | 热平衡反算允许电流 + 所需相电压峰值 + 超耐压标红（5.3 / 5.4） |
| 候选型号在样册里翻、在 Excel 里比，口径散落 | 统一电机库 + 两条准入 + 余量升序的单一推荐列表（6 / 7） |
| 交付给客户的材料靠人工拼图 | 按"轴下全部方案"导出的 PDF 报告，含封面、目录与逐方案曲线（3.3） |

### 1.3 典型使用场景（沿用需求 1.3，补充其在系统中的落点）

| 场景 | 系统内的动作路径 | 依赖模块 |
|---|---|---|
| 售前快速选型 | 填距离/时间/负载 → 读理论结果 → 看推荐列表 → 选一台 | M4 → M6 → M7 → M8 |
| 同轴多方案对比 | 新建多条方案（不同节拍或不同电机），翻页对比 | M3（+ M6/M7/M8 逐方案重算） |
| 厂商参数库维护 | 手工录入电机，字段按类型换模板、必填校验后入库 | M10 |
| 交付文档 | 导出报告，目标"另存为 PDF"自选路径 | M11 |

### 1.4 成功判据（可作为后续验收的锚点）

| 判据 | 依据 |
|---|---|
| **可复算**：任一输出都能用界面上的输入与所选型号参数重现 | 第 45 轮（对齐参考软件，偏差 < 1%）、第 47/48 轮 |
| **可对照**：两阶段解耦，理论值只随输入变，选电机不改理论值 | 5.2 |
| **显式失败**：冲突一律报错并给出可行边界，不静默降档 | 4.2C / 4.3 / 9 |
| **单一数据源**：电机字段一套定义，录入/判定/详情/报告共用 | 6.2、6.4 |

## 8. 待确认问题清单（**已全部闭合，结论见第 10–11 章**）

> 分级说明：**P0 = 阻塞架构与数据模型**、**P1 = 影响模块边界或交付口径**、**P2 = 细节/文案**。
> 本节保留**提出时**的问题描述与候选选项以留存决策依据；**用户裁定**见第 10、11 章。

### 8.1 P0（阻塞）

#### P0-1 数据层级：页签是否等于"轴"？v1 是否需要多轴？

- **现状**：需求 3.1 为"项目 → 轴（多根）→ 方案（多条）"；原型只有**一个**轴名称输入框，两个页签各自维护一份方案列表（`state.books.linear / rotary`）。
- **为什么问**：这决定"方案归属哪个轴"、"报告范围是'轴下全部方案'还是'页签下全部方案'"，也决定数据模型是三层还是两层。
- 候选：
  - **A（倾向）**：v1 明确"页签 = 轴"，一根轴只能是直线或旋转，不做多轴切换；轴名称对两个页签共享仅作抬头。改动最小，与原型一致。
  - B：页签只是"运动形式视图"，一个项目可含多根轴，界面需增加轴切换器（新增交互，需求未定义）。
  - C：数据模型保留多轴，v1 界面只暴露第一根轴（模型先行、界面后补）。
- **影响**：数据模型层级、报告"按轴导出"的取值范围、M3 的归属。

#### P0-2 交付形态：单机离线自包含，还是 C/S（后端 + 数据库）？

- **现状矛盾**：需求 1.4 写"单用户离线桌面应用，不依赖网络"、3.2 无持久化；而项目规范（`CLAUDE.md`）给出 Java（Spring Boot 3 + MyBatis-Plus + MySQL + Redis + MinIO）与 Vue3 前端规范，并预留 `doc/rules/database-rules.md`、`doc/rules/api-rules.md`。
- **为什么问**：若走 C/S，模块划分需新增"电机库服务/库管理"边界、并启动数据库与 API 设计；若纯本地，则库文件/嵌入式存储即可，M10 的职责收窄。这直接决定第二、三阶段要产出哪些文档。
- 候选：
  - **A**：纯本地自包含（前端 + 本地计算，库落本地文件/嵌入式库），不引入服务端。
  - **B**：C/S（前端 + Spring Boot + 数据库），电机库集中存储。
  - C：先按 B 的契约设计、v1 以本地实现交付（同一前端内核算，后续接服务端）。
- **影响**：模块边界（是否新增服务端模块）、后续阶段文档集、部署方式。

#### P0-3 电机库如何持久化？（v1 必须回答，需求未定义）

- **现状**：需求只删除了"保存工程"，但**电机库必须跨会话存在**（"厂商参数库维护"是核心场景）；原型 `state.motors = D.motors.list.slice()` 是内存数组，刷新即丢。
- **为什么问**：决定 M10 是否需要"库的加载/写回/备份/版本"能力，以及数据模型里电机表的边界。
- 候选：
  - **A（倾向）**：v1 落本地（JSON 或嵌入式库），录入即写、启动即读，并提供手动备份/恢复。
  - B：只读预置库 + 会话内新增（不落盘）——与核心场景冲突。
  - C：随 P0-2 走服务端库。
- **影响**：M10 职责、数据模型、是否需要"库文件格式"设计。

#### P0-4 设置归属：运动模式 / S 曲线 / 安全余量 是页签级还是方案级？

- **现状**：原型中模式、S 曲线开关、τ、余量上下限为**页签级**（切方案不重置、切页签保留）；曲线形状与 `motorId` 为**方案级**。需求 8.2 把它们放在同一左列，未说明归属；报告封面却按全局口径写"运动模式 / S 曲线"。
- **为什么问**：决定新建方案时哪些设置继承、两条方案能否用不同模式、报告是否需要逐方案标注模式。
- 候选：
  - **A（倾向）**：全部页签级（当前基线），方案只存工况与形状、`motorId`。
  - B：全部方案级（每条方案独立记忆模式/S 曲线/门槛），便于同轴多节拍对比。
  - C：模式与形状方案级，S 曲线与余量页签级。
- **影响**：数据模型字段归属、M3 新建方案的继承规则、M11 报告结构。

## 12. 本轮快照

**已确认（沿用需求文档与原型基线）**

1. 计算侧只有两种运动形式（直线/音圈归直线运动，力矩归旋转），计算内核同构。
2. 一条方案 = 一次完整运动，不支持多段行程串联；同轴多条方案并存，逐条导出报告。
3. 两阶段数据流：理论结果（5 项）与所选电机的自身质量/惯量相关（CAL-26：未选电机时等同只含负载）；实际应用值（7 项）依赖所选电机。
4. 准入两条（连续/峰值能力含下限、双转速上限），下限是过滤器，上限是软警告（**呈现位置已定：行尾标签 + 报告提示**）。
5. 录入/判定/星标同源于字段模板的 `req` 标记；缺最高速度只跳过准入②。
6. v1 不做模板导入；交付物为 PDF 报告。
7. 单位口径：旋转用 °、rpm、rpm/s；母线电压报相电压峰值、不做 √3 折算。

**本轮新增结论（本次梳理产生）**

8. 界面可见模块 11 个（M1–M11）+ 支撑内核 5 个（K1–K5），模块与需求条目一一对应，无新增功能。

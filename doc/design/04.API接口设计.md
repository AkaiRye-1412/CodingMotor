## 0. 前置约束与设计原则

### 0.1 必须遵守的规范

| 来源 | 关键约束 | 本设计如何落实 |
|---|---|---|

### 0.2 接口总览（5 个接口族 / 9 个接口）

| # | 接口 | 方法 | 路径 | 所属模块 | 用途 |

> **为什么没有 DELETE**：第 63 轮已定 v1 不提供删除/停用，不加 `deleted_at`/`enabled` 列。本阶段如实不设计该接口，不预留占位。

### 0.3 两个方法学决策

| 决策 | 内容 | 依据 |
|---|---|---|
| **计算用 POST 而非 GET** | 计算本身是纯函数（幂等、无副作用），REST 语义上应为 GET。但请求体含约 12 个工况字段 + 页签级设置 + 过滤器集合 + `motorId`，嵌套结构塞进 URL 不可行，且易超长度限制。按规则 2.3「POST 用于执行非幂等操作」的例外精神，把「一次计算」建模为**创建一次计算快照**（`POST /calculations`），服务端不落库、纯计算后返回 | `api-rules.md` 2.3/2.4 |
| **路径前缀 `/api`** | 单体 jar 同时提供静态资源（Vue 产物），接口统一加 `/api` 前缀，避免与前端路由（`/`、`/assets/*`）冲突 | 第二阶段 T-2 |

## 1. 统一设计

### 1.1 统一响应信封

```json
{
  "code": "OK",
  "message": "成功",
  "data": { ... }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | string | 业务码。成功固定 `"OK"`；失败为分段错误码（见 2.3） |
| `message` | string | 人可读文案，可直接展示给用户（中文） |
| `data` | object / array / null | 业务数据；失败时为 `null` |

**HTTP 状态码与 `code` 的关系（规则 4.5：不得互相矛盾）**：

| 场景 | HTTP | `code` |
|---|---|---|
| 成功（含计算失败但协议正常） | `200` | `"OK"` |
| 参数校验失败 | `400` | `COMMON_VALIDATION_FAILED` 等 |
| 资源不存在 | `404` | `MOTOR_NOT_FOUND` |
| 唯一键冲突 | `409` | `MOTOR_DUPLICATE` |
| 服务端异常 | `500` | `COMMON_INTERNAL_ERROR` |

> **例外的处理（重要）**：计算失败（输入不足、上限矛盾、S 曲线放不下）**不是 HTTP 错误**——它是"请求合法但业务上无解"。此时返回 **HTTP 200 + `code="OK"`**，而在 `data.stage` 中标明失败阶段与原因（见 B1 响应）。理由：若用 4xx，前端无法区分「请求写错了」与「工况本身不可解」，且第一阶段 4.2 明确这是**正常的业务分支**（要在 M6 卡片区展示原因，而非报错弹窗）。

### 1.2 统一分页结构

```json
{
  "code": "OK",
  "message": "成功",
  "data": {
    "page": 1,
    "size": 20,
    "total": 137,
    "totalPages": 7,
    "items": [ ... ]
  }
}
```

| 项 | 约定 |
|---|---|
| 页码起始值 | **1**（不是 0） |
| 默认页大小 | **20** |
| 页大小上限 | **100**（超出则 400） |
| `total` | 满足筛选条件的总条数 |
| `totalPages` | `ceil(total / size)`；`total=0` 时为 `0` |

> **例外**：候选池（B1 计算响应内）**不分页**——它由服务端按准入过滤后一次返回全部（需求 7.3「不截断」、第 52 轮）。

### 1.3 参数校验与错误定位

校验失败时返回 `400`，`data` 为：

```json
{
  "code": "COMMON_VALIDATION_FAILED",
  "message": "参数校验失败",
  "data": {
    "errors": [
      { "field": "load", "reason": "总移动质量必须大于 0" },
      { "field": "supplyVoltage", "reason": "供电母线电压不能为负" }
    ]
  }
}
```

| 规则 | 说明 |
|---|---|
| `field` | 出错字段的**请求体路径**（如 `spec.kth`），便于前端定位 |
| `reason` | 具体原因（规则 5.4「尽可能指出相关字段及原因」） |
| 不暴露 | 不含 SQL、堆栈、类名、内部路径（`CLAUDE.md` Java 规范 12） |

**校验分层（与第一阶段 Q6 一致）**：

| 层 | 职责 |
|---|---|
| 前端 | 即时提示（非负钳制、留空即自动、必填星标） |
| **服务端（权威）** | 全部必填/范围/枚举/长度/主键唯一校验 |
| 数据库 | 唯一约束、CHECK、NOT NULL 作最后防线 |

### 1.3.1 派生项由服务端计算并返回（第 65 轮裁定）

> **修正一处设计矛盾**：第四阶段初稿写「派生项由前端按固定公式计算」，但第二阶段 A-1 的硬约束是「**计算公式只能存在于 `motorsizer-domain`，前端不得复刻任何公式**」。二者冲突，现按 A-1 修正为**服务端计算**。

| 派生项 | 公式 | 返回位置 |
|---|---|---|
| `prated` 额定功率 | `iCont² × r25` | C2 详情 `spec.derived.prated` |
| `pmax` 最大功率 | `iPeak² × r25` | `spec.derived.pmax` |
| `kmDerived` 电机常数派生值 | 三相：`Kt / √(1.5·r25)`；单相（音圈）：`Kf / √r25` | `spec.derived.kmDerived` |

**关键区分：**

| 项 | 说明 |
|---|---|
| `spec.km` | **用户录入原始值**，可为 `null`。C3/C4 提交、C2 返回 |
| `spec.derived.kmDerived` | **按公式算出的值**，只读。前端展示时优先用 `km`，其为空才用 `kmDerived`（第 46 轮「留空自动派生」） |
| `derived` 整体 | **不入库、不参与任何计算**（不参与准入、热校核、电压）；仅用于参数表展示 |
| 单位 | 与所依赖字段一致（如 `prated`/`pmax` 为 W；`kmDerived` 为 N/SqRt(W) 或 Nm/SqRt(W)） |

### 1.4 前端对接约定（供前端实现参考）

| 项 | 约定 |
|---|---|
| 统一封装 | `api/` 层统一解包信封：`code === 'OK'` 时返回 `data`，否则抛 `ApiError(code, message, errors)` |
| 请求取消 | 计算接口支持 `AbortController`；前端防抖 200–300 ms + 序号比对（第二阶段 A-2） |
| 加载/失败/空态 | 每个接口调用处需处理三种状态（`CLAUDE.md` Vue3 规范 9） |

### 1.4.1 前端计算边界（第 66 轮裁定，A-1 的落地口径）

> 澄清 A-1「公式只存在于 domain」的边界：**哪些前端数值操作算「公式」**。

| 前端允许做 | 是否算"公式" | 理由 |
|---|---|---|
| 非负钳制（质量/距离/时间/速度/加速度/供电 ≥ 0） | **不算** | 输入层规整，不产生业务结论；须在敲键当下完成（否则等 300 ms 后纠正体验差） |
| 留空即"自动"、方向↔倾斜角回写 | **不算** | 同上，纯 UI 状态管理 |
| `factor` 单位换算（CAL-25 起恒为 1） | **不算** | 属于"录入单位 → 内部单位"的数据规整，与 `kf`/`ke` 等物理公式无关；样册的 g→kg 在导入层完成（非计算） |
| 显示精度格式化（1 位小数 / 退 3 位） | **不算** | 展示层规则；但**判零逻辑须与服务端一致** |
| 运动规划、力/力矩、循环 RMS、热、电压、准入判定、余量、派生项（`prated`/`pmax`/`kmDerived`） | **算 → 只在 domain** | 产生业务结论、依赖业务规则 |

> **判定口径**：凡「产生业务结论」或「依赖业务规则」的计算 → domain；凡「把用户输入规整为可提交的数据」→ 前端。
> 若有争议，以「该操作是否可能因业务规则变化而需要修改」为判据——会变的是公式，不会变的是规整。

### 1.4.2 加载态与失败态约定（第 66 轮裁定）

| 场景 | 前端表现 | 依据 |
|---|---|---|
| 计算请求中 | 结果区（M6/M7/M8/M9）**半透明遮罩变灰**，数值**原地保持旧值**直到新值到达；**不清空、不闪烁** | Q1=A。避免"清空-重填"跳变；高频输入下感知延迟最小 |
| 字段模板（A1）加载失败 | **阻塞启动**，显示「加载失败，请重试」+ 重试按钮；不进入主界面 | Q7=A。模板是 M10 表单与 M8 参数表的必需数据，无它无法渲染 |
| 候选列表为空 | `candidates: []` 时显示「当前无合规型号，请放宽下限或清除勾选过滤，或补充电机库」 | Q2=A；文案见第一阶段 7.3 |
| 报告生成中 | 导出按钮变 loading，请求一直等到 PDF 返回（同步阻塞）；失败时按信封展示 `message` | Q4=A |
| 报告生成失败 | 响应 `Content-Type: application/json` + `COMMON_INTERNAL_ERROR`；前端**按 Content-Type 判断**是 PDF 流还是错误信封 | Q3=A |

### 1.6 数值业务上限（第 66 轮裁定，Q5=A）

> `DECIMAL(18,6)` 的物理上限极大（10¹²），但电机参数有合理物理范围。服务端**按字段设业务上限**，超限返回 `400` + `COMMON_VALIDATION_FAILED` 并在 `errors[].reason` 指出范围。
> 这比依赖数据库溢出报错友好得多（DB 报 SQL 异常，用户不知道错在哪）。

| 参数类别 | 字段 | 业务上限 | 说明 |
|---|---|---|---|
| 推力/转矩 | `forceCont`、`forcePeak`、`torqueCont`、`torquePeak` | **100000** | N / Nm；覆盖大推力直线电机与大力矩直驱 |
| 力/矩常数 | `kf`、`kt` | **1000** | N/Arms、Nm/Arms |
| 反电势常数 | `ke` | **1000** | Vpeak/(m/s) 或 Vpeak/rpm |
| 电阻 | `r25` | **10000** | Ω |
| 电流 | `iCont`、`iPeak` | **1000** | Arms / A |
| 温度 | `tMax` | **300** | °C（绝缘等级物理上限附近） |
| 热耗散 | `kth` | **1000** | W/°C |
| 电压 | `uBus` | **5000** | Vdc |
| 速度 | `maxSpeedPeak`、`maxSpeedCont` | **100000** | m/s 或 rpm |
| 电感 | `l` | **100000** | mH |
| 质量 | `totalMass`、`moverMass`、`coreMass`、`trackMass` | **10000** | kg / kg/m |
| 惯量 | `inertia` | **1000** | kg·m² |
| 行程/长度 | `stroke`、`coilLength`、`gap`、`polePitch` | **10000** | mm |

> **下限**：`> 0` 的参数（推力、电阻、电流、热耗散、电压、温度）下限为 0（不含）；其余选填项下限为 0。
> 上限值集中定义在 domain 的校验常量表中，**不散落在各 Controller**。

### 1.7 电机库搜索的大小写（第 66 轮裁定，Q6=A）

`C1` 的 `keyword` **不区分大小写**：服务端将其转为小写后用 `LOWER(model_name) LIKE` / `LOWER(series) LIKE` 匹配，用户在搜索框输入 `ilm` 能匹配 `ILM-12-020`。

> H2 的 `LIKE` 默认区分大小写，故必须显式 `LOWER()`；实现时注意该函数会阻止索引命中——电机库条目为百条级，全表扫描成本可忽略。

### 1.5 权限校验

**本项目无鉴权体系**（第一阶段 Q1 裁定：单用户、本机/局域网、不引入账号与权限）。因此：

| 项 | 处置 |
|---|---|
| 身份认证 | **无**（无登录、无 token） |
| 接口权限 | **无**（所有接口对本机用户开放） |
| 网络暴露控制 | 服务端**只监听 `127.0.0.1`**（第二阶段 A-3），不监听外网网卡——这是本项目的"边界防线" |
| 敏感信息 | 无密钥、无凭证、无用户数据可泄露 |

> 若未来需局域网多用户共享（第一阶段 Q1 曾列此候选但未采纳），须补鉴权后再开放监听；当前设计**不为将来预留鉴权字段**（避免为未定义功能提前建结构）。

## 2. 公共约定

### 2.1 通用请求头

| 头 | 值 | 必填 |
|---|---|---|
| `Content-Type` | `application/json`（D1 为 `application/json`，响应为 `application/pdf`） | 有请求体时必填 |
| `Accept` | `application/json` | — |

### 2.2 通用数据类型约定

| 类型 | JSON 表达 | 说明 |
|---|---|---|
| 数值（工况/参数） | number（可为 `null`） | 对应 DB `DECIMAL(18,6)`；**空值 ≠ 0**（第一阶段 X-6） |
| 枚举 | string | 取值见各接口；与 DB CHECK 约束一致 |
| 时间 | string（ISO-8601 UTC） | 如 `"2026-11-17T12:00:00Z"`；对应 DB `TIMESTAMP`（UTC，规则 R3-5） |
| 日期 | string `"YYYY-MM-DD"` | 对应 DB `DATE` |
| 标识 | number（自增 id） | 第 64 轮裁定：`motorId` 用自增 id |

### 2.3 错误码体系（第 64 轮裁定：前缀分段字符串码）

| 前缀 | 范围 | 示例 |
|---|---|---|
| `COMMON_` | 通用（校验、系统） | `COMMON_VALIDATION_FAILED`、`COMMON_INTERNAL_ERROR` |
| `CALC_` | 计算（对应第一阶段 4.2 关键分支） | `CALC_PLAN_INVALID`、`CALC_LIMIT_CONFLICT`、`CALC_SMOOTH_INFEASIBLE` |
| `MOTOR_` | 电机库 | `MOTOR_NOT_FOUND`、`MOTOR_DUPLICATE`、`MOTOR_SPEC_MISSING` |
| `REPORT_` | 报告 | `REPORT_NO_PLAN`、`REPORT_ALL_UNCOMPUTABLE` |

**完整清单：**

| 错误码 | HTTP | 场景 |
|---|---|---|
| `COMMON_VALIDATION_FAILED` | 400 | 任一参数校验失败（含 `data.errors`） |
| `COMMON_INTERNAL_ERROR` | 500 | 未预期异常（不返回细节） |
| `MOTOR_NOT_FOUND` | 404 | `id` 不存在 |
| `MOTOR_DUPLICATE` | 409 | `(modelName, configName)` 已存在 |
| `MOTOR_SPEC_REQUIRED` | 400 | 必填规格字段缺失（与 K2 `req` 同源） |
| `MOTOR_TYPE_MISMATCH` | 400 | `spec` 结构与 `motorType` 不匹配 |
| `REPORT_NO_PLAN` | 400 | 提交的方案数为 0 |
| `REPORT_ALL_UNCOMPUTABLE` | 400 | 全部方案都无法计算（第一阶段 3.3） |

> **计算类错误不走 HTTP 4xx**（见 1.1 例外说明）：`CALC_*` 码出现在 `data.stage.code` 中，HTTP 仍为 200。

### 2.4 异常处理机制

| 层 | 处置 |
|---|---|
| **全局异常处理器** | `@RestControllerAdvice` 统一拦截；不在各 Controller 重复 try-catch（`CLAUDE.md` Java 规范 10） |
| 参数校验异常 | `MethodArgumentNotValidException` → `400` + `COMMON_VALIDATION_FAILED` + `errors[]` |
| 业务异常 | 自定义 `BusinessException(code, message)` → 对应 HTTP 状态码 |
| 唯一约束冲突 | 捕获 DB 异常 → `409` + `MOTOR_DUPLICATE`（**不暴露 SQL 原文**） |
| 未预期异常 | → `500` + `COMMON_INTERNAL_ERROR`，**详情只写日志，不返前端** |

## 3. 接口详述

### A1 获取字段模板

| 项 | 内容 |
|---|---|
| 路径 | `GET /api/motor-templates` |
| 所属 | K2 字段字典 → 前端 M10（录入表单）、M8（参数表）、必填星标 |
| 用途 | 一次下发三套模板；前端启动时拉一次并缓存（第 64 轮裁定） |
| 请求参数 | **无** |
| HTTP 成功 | `200` |

**响应 `data`：**

| 字段 | 必填 | 校验 |
|---|---|---|
| `modelName` | ✅ | 长度 `1–100`；去除首尾空格后非空 |
| `configName` | ✅ | 枚举：`默认`/`串联`/`并联`（与 DB CHECK 一致） |
| `motorType` | ✅ | 枚举：`linear`/`torque`/`coil` |
| `structure` | ✅ | 须在该类型的 `structures` 内 |
| `cooling` | ✅ | 须在该类型的 `coolings` 内 |
| `bore` | 条件 | 力矩可填 `标准`/`特殊`；**直线/音圈必须为 `null`** |
| `manufacturer` | ❌ | 长度 `≤ 50` |
| `series` | ❌ | 长度 `≤ 50` |
| `sourceDoc` | ❌ | 长度 `≤ 200` |
| `sourcePage` | ❌ | 长度 `≤ 20` |
| `entryMethod` | ✅ | 枚举：`手工录入`/`识别草稿` |
| `enteredOn` | ❌ | `YYYY-MM-DD`；不晚于今天 |
| `note` | ❌ | 长度 `≤ 1000` |
| `spec` | ✅ | 对象；结构与 `motorType` 匹配 |

**规格字段校验（关键，第 67 轮评审补全）：**

| # | 规则 | 违规结果 |
|---|---|---|
| 1 | **必填 = K2 `req` 集合**：服务端从模板读取必填清单，**不硬编码**（C-B 单一来源） | `400` + `MOTOR_SPEC_REQUIRED`，`data.errors` 列出**全部**缺项 |
| 2 | **类型字段白名单**：`spec` 只允许包含该 `motorType` 模板中定义的 `key`；出现任何模板外或他类型的字段 | `400` + `MOTOR_TYPE_MISMATCH`，`errors[].field` 指出越界字段名 |
| 3 | **类型必填差异**：`torque` 的 `maxSpeedPeak`/`maxSpeedCont` 必填；`linear`/`coil` 的同类字段**可空**（第 43/44 轮） | 缺力矩双转速 → `400` + `MOTOR_SPEC_REQUIRED` |
| 4 | **单相/三相语义不可混用**：`coil` 的 `kf` 单位为 N/A、`r25` 为单相电阻、`iCont` 为 A；`linear` 的对应字段为 N/Arms、相间 Ω、Arms。**服务端只做范围校验，不做跨类型换算** | — |
| 5 | 选填字段 | 可为 `null` 或省略；`null` 与省略等价 |
| 6 | 数值范围 | 所有数值字段须为有限数；见 1.6 的业务上限表 |
| 7 | 单位 | **请求值即内部单位**（kg、N、Ω、Vdc、°C…）；音圈质量也按 kg 提交（第 63 轮；CAL-25 起模板 `factor=1`，「录入单位 = 内部单位」无一例外） |
| 8 | `derived` 字段 | C3/C4 请求体**不得包含** `spec.derived`（只读派生值）；出现则 `400`（防止前端误把派生值写回） |

**类型 ↔ 规格表的强制对应（三文档一致的职责划分）：**

| 层 | 职责 | 出处 |
|---|---|---|
| **模板（K2）** | 定义每种类型允许的字段白名单与必填集 | `01.功能模块梳理.md` K2 |
| **服务端（S1，本接口）** | 按规则 1–3、8 校验；按 `motorType` **路由写入对应规格表** | 本节 |
| **数据库** | 三张独立规格表 + `UNIQUE(motor_id)`；**无物理外键**（规则 R4-2），无法强制类型一致 | `03.数据库设计.md` §4.3 |

> **为什么数据库不能兜底**：规则 R4-2 禁止物理外键，数据库无法阻止「`motor_type='linear'` 却写进 `motor_torque_spec`」。该一致性**必须**由服务端在此处保证，不能依赖任何其他层。

**事务边界（第 67 轮评审补充）：**

```
S1 保存流程（C3/C4 共用）：
  BEGIN TRANSACTION
    1. 校验公共字段 + spec（规则 1–8）
    2. C4 额外：校验 motorType 未变（改类型 → 400 MOTOR_TYPE_MISMATCH）
    3. 唯一性校验：新的 (modelName, configName) 是否被其他记录占用（冲突 → 409）
    4. 写/更新 motor 主表
    5. 按 motorType 写/更新对应的那张规格表
  COMMIT
  任一失败 → ROLLBACK（不留孤儿行）
```

| 保证 | 说明 |
|---|---|
| **主表与规格表同事务** | 杜绝 03 文档 §4.3 所列的「有 motor 无规格行」孤儿数据 |
| **1:1 关系** | 规格表有 `UNIQUE(motor_id)`，重复写入被数据库拒绝 |
| **C4 的更新** | 主表与规格表同为 UPDATE，同一事务；若 `motorType` 未变则规格表是同一张，无跨表迁移 |

> **`factor` 换算的位置（第 63 轮裁定）**：「只存内部单位，换算在 K2」。K2 的需求是"模板下发"给前端，前端按 `factor` 换算后提交内部单位，服务端校验时按内部单位口径检查范围，不再二次换算。本文档明确此边界，避免两端重复换算导致 1000 倍误差。

**响应（成功 `201`）：**

```json
{
  "code": "OK",
  "message": "已入库",
  "data": { "motorId": 1 }
}
```

**业务规则：**
1. **同一事务**写入 `motor` + 对应规格表；任一失败整体回滚。
2. 唯一约束 `(modelName, configName)` 由 DB 兜底；冲突返回 `409` + `MOTOR_DUPLICATE`，`message` 提示「请改用其他型号名或配置」（第 39 轮）。
3. 不写 `createdAt`/`updatedAt`（由服务端生成，UTC）。
4. 不返回完整记录（避免多一次序列化；前端可用 `motorId` 走 C2）。

### C4 编辑电机

| 项 | 内容 |
|---|---|
| 路径 | `PUT /api/motors/{id}` |
| 所属 | S1 → 前端 M10 |
| 用途 | **整体替换**该电机记录（含公共属性与规格） |
| HTTP 成功 | `200`；不存在 `404`；重复 `409` |

**路径参数：** `id`（number）

**请求体：** 与 C3 **完全一致**（整体替换语义，规则 2.3 `PUT`）。`spec` 必须完整提交（不支持的"部分更新"走 `PATCH`，v1 不提供）。

**业务规则：**
1. **不允许改 `motorType`**（Q1=A，第 64 轮）：若提交值与库中不同 → `400` + `MOTOR_TYPE_MISMATCH`。理由：改类型意味着换规格表（删除旧规格行 + 建新行），属结构性变更；需求 6.4 只写"编辑"，未定义此场景。
2. **允许改 `modelName` / `configName`**（Q8=A，第 66 轮）：它们是业务主键的一部分，服务端校验新的 `(modelName, configName)` 组合是否已被其他记录占用——冲突返回 `409` + `MOTOR_DUPLICATE`。理由：录入时型号名写错是常见情况；v1 **不提供删除**，若不允许改名，错数据将无法修正。
3. 规格字段按 C3 同一套校验（必填由 K2 决定）。
4. `createdAt` 保持原值，`updatedAt` 刷新。
5. 同一事务更新主表 + 对应规格表。

> **改名与改类型的区别**：改名只动主表的标识列，规格表内容不变，是**数据修正**；改类型要换规格表，是**结构变更**。故前者允许、后者禁止。

### D1b 导出报告到自选路径（第 91 轮）

| 项 | 内容 |
|---|---|
| 路径 | `POST /api/reports/pdf/save` |
| 用途 | 先弹系统原生「另存为」对话框让用户**自选保存位置**，再生成 PDF 落盘，返回实际路径 |
| HTTP 成功 | `200`，`application/json` 信封 `{ saved, path, filename }` |
| 请求体 | 同 D1 |

**响应示例：**

```json
{ "code": "OK", "message": "报告已保存", "data": { "saved": true, "path": "D:\\报告\\General Machine-Axis 1-电机选型报告.pdf", "filename": "General Machine-Axis 1-电机选型报告.pdf" } }
```

| 场景 | HTTP | 结果 |
|---|---|---|
| 用户在选择框里点取消 | 200 | `saved=false`（不是错误，前端静默收尾） |
| 无图形环境（`GraphicsEnvironment.isHeadless()`） | 501 | `REPORT_SAVE_UNAVAILABLE` → 前端回退到 D1 浏览器下载 |
| 写盘失败（目录被删 / 无权限 / 磁盘满） | 500 | `REPORT_SAVE_FAILED`，消息只带文件名不带内部路径 |

**实现要点：**
1. 用 `java.awt.FileDialog`（Windows 原生对话框），不用 `JFileChooser`（Swing 自绘，外观与系统不一致）。
2. Spring Boot 默认把 `java.awt.headless` 置为 `true`，会让 `FileDialog` 抛 `HeadlessException`。**只在 `main()` 里** `application.setHeadless(false)`；`@SpringBootTest` 不经 `main`，仍保持 headless，所以单测调用该接口只会拿到 501，不会弹窗卡住。
3. **先弹窗、后生成**：用户取消时不必白算一遍 PDF；文件名由 `ReportService.suggestedFilename()` 容错给出（此时请求还没过校验）。
4. 对话框在 EDT 上显示（`EventQueue.invokeAndWait`），请求线程一直挂到用户选完；前端 `timeout: 0`，不会被 60s 默认超时掐断。
5. 记住上次选择的目录，连续导出多个方案时不用重新找路径；首次默认「桌面」→「下载」→ 用户目录。
